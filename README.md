## Maze Runner Windows PoC

This project is a Windows-first proof-of-concept that evaluates Flutter as a desktop UI for a simulator-style workload. It implements a simple 2D Maze Runner game where:

- A native C++ DLL (built via CMake) generates random mazes and computes A* shortest paths.
- A Flutter Windows desktop app renders the maze, shows the A* path overlay, and allows keyboard navigation.
- `dart:ffi` is used to call into the DLL with a simple C ABI and plain-old-data buffers.

Windows is the primary target; web and other platforms are out of scope for this PoC.

## Project Structure

- `pubspec.yaml` — Flutter app definition and dependencies (Flutter SDK + `ffi`).
- `lib/`
  - `main.dart` — app entrypoint, hosts `MazeScreen`.
  - `state/maze_state.dart` — mutable state for maze grid, player/target positions, path, and FPS stats.
  - `native/maze_ffi.dart` — `dart:ffi` bindings and helpers for calling the C++ DLL.
  - `ui/maze_screen.dart` — main UI: maze canvas, controls, keyboard input, stats.
  - `ui/maze_painter.dart` — custom painter to draw the maze grid, player, target, and A* path overlay.
- `native/`
  - `CMakeLists.txt` — CMake config to build `maze_lib` as a shared library.
  - `maze_lib.h` — C ABI header, error codes, and function declarations.
  - `maze_lib.cpp` — maze generation (recursive backtracker) and A* pathfinding implementation.
  - `README.md` — native-only build notes.
- `docs/findings.md` — findings on Flutter’s Windows rendering backend, Skia/ANGLE/Direct3D usage, and GPU verification steps.

The Windows runner code (`windows/` folder) is generated by Flutter and is not included here; see setup below.

## Prerequisites (Windows)

- Flutter SDK with Windows desktop support enabled.
  - Install Flutter and run:
    - `flutter config --enable-windows-desktop`
    - `flutter doctor` (ensure Windows desktop shows as supported).
- Visual Studio with the **Desktop development with C++** workload, or another CMake-capable Windows toolchain.
- CMake 3.15+ (Visual Studio installers include it; otherwise install separately).

> Note: Although this repository can be viewed on non‑Windows systems, building and running the DLL + desktop app together is intended for Windows only.

## One-Time Project Setup (Windows)

From a clean checkout of this repository on Windows:

1. **Create the Windows runner and platform scaffolding** (safe for existing Dart code):

   ```bash
   flutter create --platforms=windows .
   ```

   This command:

   - Ensures the `windows/` folder and runner executable are generated.
   - Leaves existing `lib/` code intact.

2. **Fetch Dart/Flutter dependencies**:

   ```bash
   flutter pub get
   ```

## Building the C++ DLL (`maze_lib.dll`)

1. Open a **Developer Command Prompt for VS** (or equivalent environment with MSVC and CMake on `PATH`).
2. From the project root, build the DLL:

   ```bash
   cd native
   cmake -S . -B build -G "Visual Studio 17 2022"
   cmake --build build --config Release
   ```

   - Adjust the generator (`-G`) and configuration (`Debug` vs `Release`) as needed.
   - The resulting DLL will typically be at:
     - `native/build/Release/maze_lib.dll` (for a Release build)

3. **Copy the DLL next to the Flutter Windows runner executable** so `dart:ffi` can find it:

   - For a debug run, Flutter usually places the runner at a path like:
     - `build/windows/x64/runner/Debug/maze_runner_windows.exe`
   - For a release build:
     - `build/windows/x64/runner/Release/maze_runner_windows.exe`

   Copy `maze_lib.dll` into the same folder as the runner you intend to use, e.g.:

   ```bash
   copy native\build\Release\maze_lib.dll build\windows\x64\runner\Debug\
   ```

   `lib/native/maze_ffi.dart` loads the DLL with:

   ```dart
   ffi.DynamicLibrary.open('maze_lib.dll');
   ```

   so the DLL must be on the process DLL search path; placing it next to the runner executable is the simplest option.

## Running the Flutter Windows App

From the project root on Windows (after building/copying the DLL and running `flutter pub get`):

```bash
flutter run -d windows
```

or build and run a release binary:

```bash
flutter build windows
```

Ensure that `maze_lib.dll` is present next to the runner executable in the build output directory before launching.

## Game Behavior & Controls

- **New Maze**
  - Uses the C++ DLL (`generate_maze`) to generate a random perfect maze with the selected size and seed.
  - Maze sizes: 20×20, 50×50, 100×100 (stress‑test presets).
  - Seed: integer typed into the Seed field (empty/invalid values fall back to a random seed).
- **Player movement**
  - Keyboard controls: **Arrow keys** or **WASD**.
  - Movement is constrained by walls; you cannot walk through walls, matching the DLL’s cell wall encoding.
- **Solve**
  - Invokes the C++ DLL’s `astar_path` to compute the shortest path from the player cell to the target cell.
  - The path is rendered as a yellow polyline overlay; path length and last solve time (ms) are shown in the Stats panel.
- **Toggle Path**
  - Shows/hides the A* path overlay without recomputing it.
- **Reset Player**
  - Moves the player back to the start cell (top‑left).
- **Target**
  - By default, the target cell is placed at the bottom‑right corner of the maze.

## Stats and Performance Probes

The right‑hand panel displays basic stats:

- **Maze** — current width × height and seed.
- **Path length** — number of cells in the last computed A* path.
- **FPS** — approximate frames per second, computed via a ticker and MazeState.
- **Last maze gen** — elapsed time (ms) around the FFI `generate_maze` call.
- **Last A* solve** — elapsed time (ms) around the FFI `astar_path` call.

To stress test rendering and FFI:

- Switch between 20×20, 50×50, and 100×100 maze sizes.
- Move the player continuously with the keyboard and observe FPS and responsiveness.

For GPU/backend investigation guidance (Skia, ANGLE, Direct3D, discrete GPU usage), see `docs/findings.md`, which includes:

- Documentation‑based statements on Flutter’s rendering stack.
- Task Manager and GPU utilization steps to observe GPU engines in use.

## C++ / Dart Boundary Design

- The C++ DLL exposes a **C ABI** via `extern "C"` and a stable header `maze_lib.h`.
- Maze representation:
  - Grid of `width * height` cells.
  - Each cell is a `uint8_t` bitmask of walls: `1=up`, `2=right`, `4=down`, `8=left` (row‑major order).
- A* path representation:
  - Flat `int32_t` array of `(x, y)` pairs: `[x0, y0, x1, y1, ...]`.
  - Return value from `astar_path` is the number of cells in the path (positive) or a negative error code.
- Memory ownership:
  - Dart allocates output buffers via `calloc` (through `package:ffi/ffi.dart`).
  - C++ only writes into the provided buffers; no cross‑boundary `malloc`/`free`.
- Error handling:
  - Negative return codes (`MAZE_ERROR_*`) are translated into Dart exceptions.
  - Basic debug logs (DLL load success, maze generation, path length) are printed to the Flutter console from the FFI layer.

## Notes & Limitations

- This PoC is intentionally minimal: no plugin system, no web target, no persistence.
- The rendering logic is tailored for grid‑based mazes and A* visualization; it is not a general purpose game engine.
- Graphics backend details (e.g., ANGLE vs native OpenGL vs Vulkan) are treated as implementation details of the Flutter engine + Skia; see `docs/findings.md` for what can and cannot be claimed from official sources.
