# Maze Runner PoC

A 2D + 3D maze game built as a proof-of-concept to find out what Flutter can and cannot do for a GPU-heavy, native-compute-backed cross-platform app. The maze is not the point — it's a controlled experiment that forces Flutter through the exact integration points I wanted to evaluate: native C++ compute via FFI, GPU-backed 2D and 3D rendering, custom shaders, and cross-platform portability (desktop + web).

The project brief is in `goal.md`. The nine questions with direct answers and supporting evidence are in `docs/report.md`.

## What it does

- **Random perfect mazes** generated by C++ (recursive backtracker).
- **A\* shortest path** computed by C++ on request.
- **Two views** — 2D top-down (`CustomPainter`) and first-person 3D (`three_js` with textured walls / floor / ceiling). Switch between them with the `View` toggle; both views share the same maze state.
- **Keyboard navigation**, with collision against the same C++ wall bitmask on both views.
- **Win detection** — reaching the target opens a dialog to play again or generate a new maze.

The C++ core (`native/maze_lib.cpp`, 310 lines) is unchanged across three build targets: Windows DLL, Linux `.so`, and WebAssembly.

## Architecture

```
maze_runner_windows (Flutter app)
 ├── UI (lib/ui/)
 │    ├── 2D view: maze_painter.dart + CustomPaint
 │    └── 3D view: maze3d_{view,scene,hud}.dart + three_js
 │
 ├── State (lib/state/maze_state.dart) - ChangeNotifier
 │    (cells, player, target, facing, path, FPS, view mode)
 │
 ├── Engine (lib/engine/) - platform-agnostic contract
 │    └── MazeEngineFromBackend wraps MazeBackend
 │
 └── Backend (lib/maze/)
      ├── Desktop:  DesktopFfiBackend  → dart:ffi → maze_lib.{dll,so,dylib}
      ├── Web-srv:  WebServerBackend   → HTTP     → server_cpp/maze_server
      └── Web-wasm: WebWasmBackend     → JS interop → maze.wasm
```

Conditional imports select the backend at compile time; on web, `--dart-define=MAZE_MODE=server|wasm` picks between the two web paths.

## Prerequisites

**Windows:**
- Flutter SDK with Windows desktop support (`flutter config --enable-windows-desktop`)
- Visual Studio with the "Desktop development with C++" workload
- CMake 3.15+ (VS installer bundles it)
- Python 3 (only for regenerating textures)

**Linux:**
- Flutter SDK with Linux desktop support (`flutter config --enable-linux-desktop`)
- `sudo apt install clang cmake ninja-build pkg-config libgtk-3-dev`
- Python 3

**Web (either mode):**
- Chrome (or any browser; use `-d web-server` if no Chrome available)

**Web WASM mode additionally needs:**
- [Emscripten SDK](https://emscripten.org/docs/getting_started/downloads.html) (`emsdk`), activated

## Quick start

### Windows

```bash
flutter pub get
flutter build windows --release
./build/windows/x64/runner/Release/maze_runner_windows.exe
```

The Windows CMake setup auto-builds `maze_lib.dll` and installs it next to the runner exe — no manual copy step.

### Linux

```bash
flutter pub get
flutter run -d linux
```

The Linux CMake setup auto-builds `libmaze_lib.so` into `bundle/lib/`; the runner's `$ORIGIN/lib` RPATH resolves it at load.

### Web — single-command launcher

One command builds everything and opens Chrome. Pass `wasm` or `server` to pick the backend.

```bash
# Linux / macOS / Windows git-bash:
./tools/run_web.sh wasm         # C++ compiled to WebAssembly, all in browser
./tools/run_web.sh server       # C++ HTTP server, Flutter web calls it

# Windows PowerShell:
.\tools\run_web.ps1 wasm
.\tools\run_web.ps1 server
```

In `server` mode the script builds the C++ server with CMake, starts it on port 8080, then runs Flutter web pointed at it. Ctrl+C stops both processes. In `wasm` mode everything runs in the browser — no background server to manage.

## Controls

### 2D view

| Key | Action |
|---|---|
| `W` / `↑` | move up one cell |
| `S` / `↓` | move down one cell |
| `A` / `←` | move left one cell |
| `D` / `→` | move right one cell |

### 3D view (first-person, tile-based)

| Key | Action |
|---|---|
| `W` / `↑` | step forward |
| `S` / `↓` | step back |
| `A`       | strafe left |
| `D`       | strafe right |
| `Q` / `←` | rotate left 90° |
| `E` / `→` | rotate right 90° |

Mouse is unused in both views.

### Buttons (right panel)

| Button | Action |
|---|---|
| **New Maze** | Call C++ `generate_maze` with the selected size and seed; resets player to (0,0). |
| **Solve**    | Call C++ `astar_path` from the player's current cell to the target. Stores the path as a snapshot and makes it visible. |
| **Toggle Path** | Hide / show the stored path snapshot. Does not recompute. |
| **Reset Player** | Teleport player to (0,0), clear the stored path. |

The path hint is a **snapshot**, not live — it stays as you walk, until you click Solve again. Reset Player and the "Play again" option in the win dialog both clear the stored path so you start clean.

## Tools

| Script | Purpose |
|---|---|
| `tools/gen_textures.py` | Generate 256×256 procedural brick / checker / grid PNGs into `assets/textures/`. Pure stdlib — no Pillow. |
| `tools/ffi_smoke.dart`  | Load the native lib, run `generate_maze` + `astar_path`, verify a set of invariants. Exits 0 on success. |
| `tools/ffi_perf.dart`   | Time maze gen + A* across sizes 20, 50, 100, 200. Prints a perf table. |
| `tools/build_wasm.{sh,ps1}` | Emscripten build script producing `web/wasm/maze.{js,wasm}`. |

## Stats panel

The right-hand panel displays:

- **Maze** — current `width × height` and seed.
- **Path length** — cells in the last computed A* path, or 0 if not solved yet.
- **FPS** — measured via a ticker.
- **View** — 2D or 3D.
- **Last maze gen** — FFI timing for the most recent `generate_maze`.
- **Last A\* solve** — FFI timing for the most recent `astar_path`.

In 3D mode, a HUD overlay in the top-left adds the player's grid position + facing direction and the current wall count; the bottom-left overlay is a controls reference.

## Native C++ library (`native/`)

The C++ maze generation and A\* solver live in `native/maze_lib.cpp` / `maze_lib.h` and build to a shared library via CMake:

- Windows: `maze_lib.dll`
- Linux: `libmaze_lib.so`
- macOS: `libmaze_lib.dylib` (header-ready; not yet wired into a Flutter runner)

**You normally don't build this directory directly.** `windows/CMakeLists.txt` and `linux/CMakeLists.txt` each pull `../native` in as a CMake subdirectory, so the shared library is built and installed next to the Flutter runner automatically — no manual copy step. `lib/native/maze_ffi.dart` finds it by trying `<exe_dir>/lib/<libname>`, `<exe_dir>/<libname>`, and the plain file name.

### Exported C API

```c
int generate_maze(
  int width, int height, int seed,
  uint8_t* out_cells, int out_cells_len);

int astar_path(
  const uint8_t* cells,
  int width, int height,
  int sx, int sy, int tx, int ty,
  int32_t* out_path_xy, int out_path_xy_len);

int query_gpu_info(char* out_buffer, int out_buffer_size);
```

### Return codes

- `0` — success.
- `-1` — invalid arguments.
- `-2` — output buffer too small.
- `-3` — no path exists between start and target.
- `-4` — internal error.

### Cell and path encoding

Each cell in `out_cells` is a `uint8_t` bit-field: `1 = wall up`, `2 = wall right`, `4 = wall down`, `8 = wall left`. Row-major order: `index = y * width + x`.

`astar_path` writes `(x, y)` pairs as consecutive `int32_t`s into `out_path_xy`, from start to target inclusive. The return value on success is the number of cells in the path.

### Building standalone (only if iterating on C++ alone)

```bash
# Windows
cmake -S native -B native/build -G "Ninja"
cmake --build native/build --config Release
# -> native/build/Release/maze_lib.dll

# Linux
cmake -S native -B native/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build native/build
# -> native/build/libmaze_lib.so
```

Symbol visibility on Linux/macOS is hidden by default (CMake `CXX_VISIBILITY_PRESET hidden`); only `MAZE_API`-decorated functions export, matching MSVC's default. `MAZE_STATIC` is defined for the static-linked server build in `server_cpp/` and removes the export decoration entirely.
